## 确定的应用缺陷与仍未知部分

cf62发送泵原实现以单个 inFlight 为闸门：前一条 ws.send 的本地写回调未返回，就不调用下一条音频send。20ms/640B输入因此要求长期平均回调速率能跟上帧率；多次局部慢回调会累积成应用排队，即使实际 socket 缓冲很小，也触及既有2秒/64k保护。cf62与0bd的该文件 Git blob完全相同，不能继续只归因容量补丁。

这是已通过源码和可控实验确认的应用层放大机制，不是对真实慢回调底层原因的定论。ws回调仅为本地写进度，不等于供应商接收、识别或消费确认。

local多次慢回调等待期间，remote仍有写完成事件，因而不支持把整个400—600ms区间直接解释为全局事件循环冻结。30秒采样的一小时资源摘要 CPU_USAGE最大0.08374、内存最大0.09326GB，未给出资源耗尽证据，也无法排除瞬时阻塞。130条network-flow元数据未记录dropCause，latencyMs均为0；该字段不具备逐帧RTT/供应商ACK含义，不能据此认定网络正常或归因阿里。

仍缺：每帧真实底层socket/TLS/压缩诊断、事件循环延迟、精确供应商接收确认。无本通原音，没有试听整通或付费转写。不关闭压缩、不调整资源或网络配置来猜测修复。

## 最小修改

- 相邻音频append按既有FIFO调用ws.send，允许有界多条在途，不再逐帧等待前一条回调。
- pending仍包含所有未确认、已完成但前缀缺口未闭合的写；原64000B PCM、1MiB wire/socket与2000ms受理到完成期限全部保留，未扩大常量或延长超时。
- 回调可先到，但只有连续成功前缀才能公布writtenAudioBytes和onWritten；重复、迟到回调不能二次计数、重复发送或串入新状态。
- session.update、session.finish及非音频消息保留完整回调屏障。每条只有一次send尝试，没有重试、重放、重连、丢帧或静默吞错。
- 真实写错误、持续背压或未回调仍明确失败，沿原路径停止翻译并清理两侧模型，保留原声及用户挂断。

只新增一个内部回调耗时字段和有界在途数组，未修改公开模型/协议类型、翻译内容或播放逻辑。每个正常640B音频帧占用原64k总预算，最多100个未确认音频帧；字符串仍受既有wire总预算限制。

以下为人工构造实验，不冒充完整真实供应商回放：

- 健康1ms、20ms路径：前后wire全文hash、字节、send时刻、回调与onWritten顺序/时刻和终止结果一致。1ms诊断全序也相同；20ms同一时刻append与前条callback竞争时，诊断send_started/send_written相对先后有预期差异，业务时刻/顺序不变，完整trace已保存。
- 独立localhost真实WebSocket传输，加人为630.701ms回调延迟：旧版只让peer收到4帧即超时；候选140帧全部按序到达，无重复，pending峰值20480B。这验证客户端机制，不是阿里连通性或实通时延。
- 保留真不回调两版均2秒失败、持续高buffer、关闭/发送竞态、乱序/重复回调、配置/finish屏障、双向隔离及取消挂断测试。

真实日志只回放/核对可取得的元数据；没有原始PCM或全部回调，因此不声称完整复现本通每一帧的供应商轨迹。
